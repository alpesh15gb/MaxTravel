# Travel CRM staff-workflow benchmark — 25 October 2026

## Decision

Trust should come from correct state, clear next steps, exact-record handoffs and recoverable failures, not badges or a busier dashboard. Preserve MaxTravel's existing Today queue, scoped customer history, private drafts, one-time proposal links, unknown-save locks, receipt/refund semantics and WhatsApp recipient confirmation. Improve the gaps remaining in that workflow before adding automation.

This is a comparison of eight relevant travel platforms, **not an independently validated market ranking**. Evidence is from public official product/help material read on 25 October 2026. No vendor account was created, no demo attended, no vendor app operated, and no security/compliance assertion independently verified. Marketing capabilities are distinguished from documented workflows. Plan, regional and contractual limitations may apply. Feature absence from a page is not evidence of product absence.

## Concrete MaxTravel changes from source inspection

1. **Prevent silent stage/follow-up overwrites.** Draft quotation saves already checked the loaded revision, but stage updates did not. Require the same all-version revision for stage writes, reject stale/missing revisions with an explicit 409, preserve the editor text and let staff Refresh intentionally. No schema, permission or money change.
2. **Protect accepted historical versions.** A customer can accept an earlier published proposal while a newer draft remains private. Checking only the newest version allowed contradictory new drafts/publication. Any accepted version now blocks these replacement actions until staff handles that acceptance explicitly. Existing conversion idempotency is retained.
3. **Make the actual next step visible.** A read-only enquiry summary prioritizes the linked booking, closed state, accepted version, latest draft, then outstanding proposal. Its review button only focuses the exact quote; it never saves, publishes, sends or creates financial records. The customer code is displayed alongside the name to reduce same-name mistakes.
4. **Separate deadline from acceptance.** A recorded accepted proposal is not relabelled “Expired” after its old offer deadline. Expired offer guidance applies to unaccepted drafts/published proposals, not completed acceptance or linked bookings.

### Implementation verification

- Passed with the lockfile dependencies: Prisma client generation, TypeScript, ESLint, production Next.js build, helper/revision tests, action/draft/customer memory tests, handoff-controller tests, branch/workflow regression tests and customer-history fixtures.
- Passed `tests/staff-sales-flow.mts` against a newly migrated **synthetic** `prisma/security-verification.db`, using the production build and a loopback server. New assertions verify stale stage/follow-up and stale withdrawal rejection; no successful-write audit on rejection; historical accepted version conversion at its own price/cost; unchanged acceptance name/time on replay after expiry; rejection of unaccepted expired offers; conflicting historical acceptance refusal; and the acceptance-versus-replacement race invariant. Existing authentication, scoped discovery and finance regressions also passed.
- Withdrawal now includes an enquiry-revision check and version/state-specific confirmation. This closes the race where staff sees a published offer but the customer accepts before withdrawal. Acceptance name/time and its audit remain preserved when staff deliberately withdraws an accepted version.
- Legacy multiple accepted/linked versions are shown as a conflict, not silently resolved by selecting the latest version. New acceptance/conversion is refused when another accepted/linked record conflicts. Repeating an already-linked conversion still returns the original booking.
- Browser test `tests/sales-operational-trust-browser.mjs` is wired into the existing UI metrics gate and saves `test-artifacts/sales-trust-mobile.png` when executed there. It is **authored and syntax checked, not locally browser verified**. Actual CI browser, screenshot review and integrated-branch checks remain required.
- Initial local dependencies were stale. An initial build failed on unsupported `--webpack`; `npm ci` first failed because its default cache could not be created, then succeeded with `/tmp/crm-staff-npm-cache`. The final build used the lockfile version and passed. No permission escalation or protected-path access was used. Build warnings about the existing middleware convention and Next.js Edge-runtime imports remain; no claim that these warnings were fixed.
- Independent review reran the standard HTTP suite on a separate fresh synthetic DB and added acceptance/withdrawal and conversion concurrency checks. Those assertions were then committed into the standard suite and rerun successfully on another fresh DB: three concurrent acceptance/withdrawal attempts observed acceptance win (200/409); two conversion pairs both returned the same booking (200/200) with exact ₹153.08 sale / ₹86.42 cost, correct customer/branch and one booking audit; deliberate accepted withdrawal retained acceptance evidence. A deterministic withdrawal-first test then proved later token acceptance returns 404 without consent/audit. This verifies observed orderings, not an exhaustive scheduler proof. Reusing an old fixture DB is outside the suite's fresh-database contract; its generic discovery searches can otherwise see earlier synthetic rows.
