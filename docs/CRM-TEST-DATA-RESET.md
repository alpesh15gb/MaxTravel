# Owner-requested CRM test-data reset

`scripts/vps-reset-crm.py` is a Linux root operator tool for the current SQLite CRM deployment. Default mode inspects only. `--apply` clears business test records across the entire CRM workspace, not just records assigned to the specified owner. The owner email must uniquely identify an active OWNER or SUPER_ADMIN. The booking app/database are never selected or changed.

By default, the tool preserves staff accounts/passwords/sessions/MFA, branches/roles, settings and credentials, reference counters, visa/checklist/work templates, the marketing catalogue/media, security audit history and processed booking-event deduplication. It clears clients/travellers/cases, visa/booking source records, invoices/receipts/credits/refunds/journal, suppliers/settlements, sales, documents/upload capabilities, tasks/history, CRM message history, notifications, import batches and customer/booking integration links. Document-access logs associated with removed documents are cleared; by default the master security audit remains and receives a reset entry. Retired provider configuration and queues are removed by the messaging retirement migration.

The tool checks the exact known database schema, database integrity, foreign keys, active owner, uncertain external commands and other containers that could write the CRM database. It uses the checksummed deployment helper to retain the authoritative live Compose configuration, volumes, environment and image. Only the CRM app and its already active workers are paused.

Before changing live data, the existing full backup tool captures SQLite, private uploads and package media, and its restore tool verifies that backup. An independent SQLite snapshot is cleared offline in one transaction. Every preserved table is compared before/after; business tables must be empty, schema unchanged, and integrity/foreign-key checks clean. Native SQLite backup installs that verified candidate atomically, handling existing WAL journals without replacing the live filename or deleting sidecars. The same CRM image restarts and must become healthy before prior workers resume. No rebuild or migration reset is needed.

If backup/candidate preparation fails, original services resume with original data. If installation succeeds but startup verification fails, the tool does not automatically overwrite potentially newer data with an old backup; keep the recovery directory and review service status. Private snapshot/configuration files and previous uploads remain for recovery. Removed upload capabilities no longer authorize old documents through the app. This is an application fresh slate, not secure erasure of backups or storage.

The helper file must match SHA-256 `5b88f65d42e5b006cdfecc092c254c9196669bb5762ef776a1e75027f44a5fac` (the pinned two-app updater from MaxTripJack commit `3412b7d0438e27ae9cca25f2b4e2e98af1c38b58`). Supply it with `--helper PATH`. Pass the owner work email privately on the VPS with `--owner-email EMAIL`. Do not share private backups, settings or logs.

Tests: `python3 -B -m unittest discover -s tests -p test_vps_reset_crm.py`. They apply every committed SQLite migration to disposable databases and cover preserved authentication/settings/audit/deduplication, complete business clearing, unknown schemas, wrong/inactive owners, unresolved commands, transaction rollback, existing WAL files, persistent-mount validation, inspection-only behaviour, backup-before-reset/restart ordering, backup failure recovery and unknown writers.

## Separate audit-history cleanup

Use `--audit-only` to clear only the CRM AuditLog history, without repeating the business reset. It uses the same verified full backup, offline candidate, atomic SQLite installation and healthy restart procedure. Every other table, including any new business records created after the previous reset, must remain unchanged. One new `AUDIT_HISTORY_CLEARED` entry records the actor, time and cleared-row count. Without `--apply`, this option only prints the audit-row count. Subsequent normal activity can create further new audit entries.


## Combined fresh slate and business numbering

Use `--clear-audit` with the business reset to clear existing audit history in the same backup/transaction/install. One new `TEST_DATA_RESET` entry records the action. Use `--reset-business-numbering` only when intentionally restarting test business references. It removes the known `CASE`, `C`, `VC`, `BK`, `INV`, `CN`, `RCP`, `RF` and `DOC` counters, including legacy casing variants. New business references start at `0001` for the current year and existing prefixes. Internal record IDs are not a sequence that needs resetting.

Employee/staff references, their `EMP` counter, unknown/future counters, custom case-prefix/default-owner settings, all staff/logins/roles/branches, existing encrypted fields and credentials remain unchanged. The server encryption key and its private host file are not edited. `--audit-only` cannot be combined with a business-numbering reset. Without `--reset-business-numbering`, business counters retain their previous values.

The requested all-test-data reset uses `--clear-audit --reset-business-numbering --owner-email EMAIL`, first for inspection and then with `--apply`. Only the CRM and its already active workers restart from their existing images; there is no application build, migration, payment action, supplier call or booking-app reset.

Additional checks: `node --import ./scripts/standalone-server.mjs --import tsx tests/crm-reset-numbering.mts` runs the real reference allocator and case creation after clearing a migrated disposable SQLite database. It verifies all nine business references restart, a custom case prefix remains, employee numbering continues, and an existing encrypted staff field still decrypts with the same key. The Python suite covers combined audit/counter clearing, whole-transaction rollback on counter failure, unknown counters, inactive/wrong owners, inspection-only mode, backup/restore/atomic installation and preserved-table hashes after installation.
